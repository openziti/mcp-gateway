# 2026-08-25

Built the hand-run end-to-end smoke suite in `e2e/` after the SSE-to-Streamable-HTTP conversion. Behavior is documented in `docs/current/smoke-suite.md`; these are the parts the tree doesn't show.

**Fabric-only was a decision, not an oversight.** `mcp-tools` can dial zrok and Agora and nothing else, so no test of the full trifecta can run without a live fabric and enrolled host state — the loopback seam `gateway.NewWithListener` opens is unreachable from the client side. Adding a direct-endpoint target to `mcp-tools` would make the whole path CI-able; that was raised and deliberately declined for now, since the suite is meant to be hand-run before a release rather than gated in CI. Don't read the missing CI integration as an omission.

**Backend subprocess accounting is coupled to the binary name.** `backendChildren` in `e2e/harness.go` finds per-session backends by scanning `/proc` for children whose `comm` is exactly `mcp-filesystem`. Rename or relocate that binary and the lifecycle scenarios stop counting anything — they fail as "expected 1, still have 0", which reads like a resource leak rather than a broken probe. It is also Linux-only by construction.

**A CLI-negative scenario was tried and dropped.** Driving `mcp-bridge --network=agora --share-token ...` looks like a way to smoke the one-network-per-invocation rule from the CLI, but `Config.Validate` reaches the `share_token requires zrok.share.enabled` check first, because `--network=agora` disables zrok before validation runs. The dual-network message is unreachable by that route. Config negatives stay in the unit tests where the error ordering is explicit.

**`TestGatewayChainsAgoraBackend` serves over zrok on purpose.** Serving the gateway over Agora *and* dialing an Agora backend would make a failure ambiguous between the two Agora paths. Serving over zrok isolates the failure to the backend dialer. Same reasoning would apply if a zrok-backend-over-Agora-serve cell is ever added.
