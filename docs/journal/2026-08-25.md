# 2026-08-25

Built the hand-run end-to-end smoke suite in `e2e/` after the SSE-to-Streamable-HTTP conversion. Behavior is documented in `docs/current/smoke-suite.md`; these are the parts the tree doesn't show.

**Fabric-only was a decision, not an oversight.** `mcp-tools` can dial zrok and Agora and nothing else, so no test of the full trifecta can run without a live fabric and enrolled host state — the loopback seam `gateway.NewWithListener` opens is unreachable from the client side. Adding a direct-endpoint target to `mcp-tools` would make the whole path CI-able; that was raised and deliberately declined for now, since the suite is meant to be hand-run before a release rather than gated in CI. Don't read the missing CI integration as an omission.

**Backend subprocess accounting is coupled to the binary name.** `backendChildren` in `e2e/harness.go` finds per-session backends by scanning `/proc` for children whose `comm` is exactly `mcp-filesystem`. Rename or relocate that binary and the lifecycle scenarios stop counting anything — they fail as "expected 1, still have 0", which reads like a resource leak rather than a broken probe. It is also Linux-only by construction.

**A CLI-negative scenario was tried and dropped.** Driving `mcp-bridge --network=agora --share-token ...` looks like a way to smoke the one-network-per-invocation rule from the CLI, but `Config.Validate` reaches the `share_token requires zrok.share.enabled` check first, because `--network=agora` disables zrok before validation runs. The dual-network message is unreachable by that route. Config negatives stay in the unit tests where the error ordering is explicit.

**`TestGatewayChainsAgoraBackend` serves over zrok on purpose.** Serving the gateway over Agora *and* dialing an Agora backend would make a failure ambiguous between the two Agora paths. Serving over zrok isolates the failure to the backend dialer. Same reasoning would apply if a zrok-backend-over-Agora-serve cell is ever added.

And README plus getting-started both document `zrok2 create share <name>` with a positional name, which that CLI rejects — the flag is `-s`. Flagged to Michael, not yet carded; the stdout/stderr defect from the same sweep is carded at `docs/future/roadmap/token-output-shares-stdout-with-logs.md`.

## isolating mcp-tools HTTP backend sessions

Fixed the carded defect: `mcp-tools http` connected one fabric MCP session in `Client.Start` and served every local Streamable HTTP session from it, so multiple agents behind one proxy shared a single remote session. The shape of the fix is `mcp-bridge`'s, ported onto the fabric transport instead of a subprocess. These are the parts the diff doesn't explain.

**The `streamable` package exists because of an import cycle.** Reusing `gateway.StreamableSessions` from `tools` is impossible: `gateway/session.go` and `aggregator/backend.go` both import `tools` for `tools.Access`, so `tools` cannot import `gateway`. Three ways out — extract the session set to a leaf package, move `Access` out of `tools`, or copy the ~50 lines — and extraction won, since the set is a transport-lifecycle primitive with three consumers and not a gateway detail. Moving `Access` is the other real cleanup available (server-side packages reaching into the client package for a fabric primitive is the actual layering smell), but it is a different job and leaves `tools` depending on `gateway`, which is upside down.

**`Sessions.Handler` was silently dropping options.** It hardcoded `&mcp.StreamableHTTPOptions{SessionTimeout: ...}`, which was fine while only the gateway and bridge called it — neither offers stateless or JSON-response modes. `mcp-tools http` does, and routing it through the shared handler would have quietly disabled both flags. Hence `streamable.Options`.

**The backend session context must outlive process shutdown, and nothing but Close may cancel it.** `bridgeSession` holds a `ctx`/`cancel` pair because `exec.CommandContext` binds the subprocess to it, and cancelling *is* the teardown. Over the fabric it is the opposite. `mcp.Client.Connect` derives the connection's lifecycle context from the one it is passed (`streamable.go:1280`) and builds the closing Streamable HTTP `DELETE` on it (`streamable.go:1745`) — and that DELETE is the only thing that makes the far-side gateway release the client's dedicated backends. Any path that can cancel that context early strands the remote session until the far side's idle timer reaps it, up to thirty minutes.

I got this wrong twice. First by connecting on the signal-driven process context, having checked that Connect's ctx does not govern session lifetime and wrongly concluded it was inert. Then by keeping a `context.AfterFunc(ctx, cancel)` over the handshake to make shutdown interruptible — which reintroduces the same failure through a narrower door, because a `Connect` can succeed exactly as the cancellation lands, yielding a live session with a dead context. The SDK uses one context for both the handshake and the connection's lifetime, so there is no way to have both an interruptible handshake and a guaranteed-live cleanup context. The resolution is to bound the *wait* instead of the handshake: sessions connect on `context.WithoutCancel`, and `Stop` waits up to `httpShutdownTimeout` for in-flight creations before releasing the fabric, logging any it abandons. A session abandoned that way is the one accepted residual, and idle expiry is its backstop.

That residual is worse than it first looks, and terminus is what sharpened it. I had described it as a session that never finished connecting. It is not: the far side creates its session and spawns its backends the moment the `initialize` request *arrives*, so a handshake whose response is stalled means a real remote session already exists, already holding subprocesses, while this side has no session object to close. It is unreleasable by construction. The bound was kept anyway — the alternative is waiting indefinitely, and with no timeout on any fabric HTTP client in this repo that turns a wedged overlay into a shutdown that never completes. A slow Ctrl-C is a worse failure than a session the far side reclaims on a timer.

**Shutdown is three separate races, and steady-state tests see none of them.** Terminus found all three, across three rounds, after my own tests were green: the process context cancelling the DELETE; `removeBackendSession` untracking before closing, so `Stop` could release the fabric under an in-flight close; and `Stop` snapshotting the session set while a handshake was still running, so a session could register after the snapshot. All three end the same way — a remote session held until idle expiry — and none were reachable by a test that closes its frontends while the process is still healthy. `Client.mu` now guards the whole lifecycle: the tracked set, the in-flight creation count, and the shutdown flag. `removeBackendSession` closes before untracking, which works because the SDK guards `Close` with a `sync.Once`, so `Stop` closing the same session waits for the in-flight close rather than racing it.

**Stateless mode opens a fabric session per request.** The SDK calls `getServer` for every request in stateless mode and closes the session before the request returns, so per-request ownership falls out of the same handler with no extra code. It is correct and it is expensive — a full MCP handshake across the overlay per call. Documented rather than hidden; the alternative was rejecting `--stateless` outright.

**`Client.serve` exists for testability.** `Run` is two lines over it because `mcp.StdioTransport` binds the test process's stdin; `serve` takes a transport, so `TestStdioServeOwnsOneBackendSession` can drive it over `mcp.NewInMemoryTransports` and prove the single-frontend path opens and releases exactly one backend session.

**The isolation test was mutation-checked.** Reintroducing the shared-session behavior in `createHTTPHandler` makes `TestHTTPFrontendSessionsGetIsolatedBackendSessions` fail on its `firstID != secondID` assertion, so the test is load-bearing rather than merely green. The mutant then hangs in test cleanup — its stub cleanup leaves a parked stream that blocks `httptest.Server.Close` — so run any repeat of that experiment under `-timeout`.

Unrelated to this work and left alone: the stdio `transport.protocol` rejection in `aggregator/config.go` and its changelog entry were already in the working tree when I arrived.


**The same context-ordering bug was already in the gateway.** `gateway.ClientSession.Close` called `cs.cancel()` before its backend-close loop. For stdio backends that is fine — cancelling is how the subprocess dies — which is exactly why it reads as correct. For `zrok`, `agora`, and `http` backends the close is a Streamable HTTP `DELETE` on the connection context, so cancelling first stranded the *downstream* gateway or bridge session: a client disconnects, the gateway believes it cleaned up, and the far-side bridge holds that client's subprocess for thirty minutes. Fixed by closing before cancelling, mirroring `backendSession.Close`.

No existing test could catch it. `TestGatewayReleasesBackendsOnClientDisconnect` watches the gateway's own children, and its backends are stdio, so the ordering never mattered there. `TestGatewayReleasesChainedBridgeOnClientDisconnect` is the new one: it points a gateway at a bridge over zrok and watches the *bridge's* child count, which is the only place this failure is visible. Terminus found the defect by analogy after I fixed the identical shape in `tools`.

**Canon drift, flagged not fixed.** The `constructor-convention` quality asks for `new<Type>` on unexported constructors, and `bridge.createBridgeSession` — the direct model for `tools.newBackendSession` — uses `create<Type>`. Terminus flagged the new function, not the old one, so following the canon here made the two siblings disagree. The canon lives in `terminus-canon` and is not the implementation agent's to edit; recording it here so the divergence is a known choice rather than a discovered inconsistency.

**What terminus was worth, concretely.** Nine rounds. Round 1 was cosmetics. Rounds 2, 4, and 5 each found a distinct shutdown-path defect that would have shipped, none reachable by the tests I had written, all ending in remote sessions held for thirty minutes. Round 7 found the same context-ordering bug sitting in the gateway, by analogy to the one just fixed in `tools`. Rounds 8 and 9 ran out of findings in this card's code and began auditing pre-existing `bridge` and `aggregator` issues in files touched by a single line, which is the signal that file-scoped review has converged on the change and moved on to its neighbourhood. Five roadmap cards came out of that tail: the gateway shutdown leak, the `Access` layering inversion, cross-transport field validation, wrapper capability inference, and defaulted publish refusing bridge startup.

The lesson worth keeping is narrower than "review works." Every defect it found lived on the shutdown path, and every test I wrote closed its frontends while the process was still healthy. Steady-state coverage of a lifecycle is not coverage of that lifecycle.
